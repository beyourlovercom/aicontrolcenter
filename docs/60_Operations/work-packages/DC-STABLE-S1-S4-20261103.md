## S2 — Device status truth (Issue #56)

**Bug:** Existing `remote_list_devices` returns static `READY` even when a registered device is offline. Smallest safe source fix:

- Add `createDeviceReachabilityView` on the existing fixed **four-device registry**. The existing signed fixed-target read-only `agentGet(deviceId,'/v1/tools')` transport supplies evidence. Cache responses for 15 seconds, deduplicate concurrent probes and use the transport's existing bounded request timeout (10s). No new signing keys, dynamic endpoints, arbitrary paths, commands, auto-schedulers, Agent updates or Cloudflare changes.
- The endpoint is not an independently Agent-signed health receipt. Use lowercase states **reachable / unreachable / unknown**, `registered:true` and `verified:false`. Never claim cryptographic signed-health proof or READY from this probe. Offline / request error is `unreachable` with sanitized reason; nonoperator returns `unknown` without Agent probes.
- Feature `BYL_MCP_DEVICE_LIVE_STATUS_ENABLED` defaults **OFF**. With the flag absent/0, the old static `READY` response and internal Bearer behavior are preserved byte-for-byte. With flag ON for approved OAuth Operator, list only four fixed device IDs with status as observed by the current server-owned signed request transport. Fail before binding if the trusted resolver is absent or feature flag invalid.
- Preserve R9 Operator Policy 21/21/21/22 and R12 Windows/007windows UTF-8 selftest unchanged. No release to Production merely because a Dev PR exists.

**S2 gates:** Dev source and offline/timeout/recovery/cache/invalid-payload tests; SDK four-device in-memory UAT; GitHub CI exact HEAD; separate main merge Owner `pass`; separately controlled OAuth-only Production release and authenticated real-device UAT (including a safely simulated offline transition, not forcibly disconnecting READY devices). ## S3 — Service-level recovery and rollback

**Incident:** R9 launchd `bootstrap` once returned macOS error 5 (EIO). This incident's unique root cause was not conclusively determined. A subsequent protected detached single-OAuth-service runner successfully waited for the old registration and port to clear, applied a single environment flag change, bootstrapped the same launchd service, confirmed a fresh PID/health and preserved rollback files. Never claim EIO was eliminated universally.

- Approved original OAuth public modules, original private Operator Policy and original launchd plist remain on the **US Mac service owner** in an owner-only release directory, with private directory 0700 and protected backup/config files 0600. Exact installed runtime directory and release identity are saved privately, not uploaded.
- The host now has a one-command **read-only recovery check**: run the local protected `r9-service-rollback.mjs --check`. The tool verifies service health, live module and Policy hashes against the approved candidate, original backups and filter state. Tested in Production as **PASS** without modifying the running service (PID 93871).
- A separate `--restore` is designed for an explicitly approved emergency rollback **only**, never scheduled or executed as part of S3 Dev acceptance. It refuses source/version drift, stops only the OAuth service, waits for listener quiescence, restores original files, safely re-registers OAuth, and requires health 200 / unauthenticated 401 / filter OFF before declaring success. It does not restart macOS, Chrome, Agent or other devices.
- Any `launchctl bootstrap` EIO triggers a STOP, immediate read-only status check and recovery; do not run multiple blind bootstrap/kickstart commands. Sensitive file paths, signing keys and production snapshots stay off GitHub.

**S3 current state:** Recovery artifact installed and **read-only check verified**. Destructive rollback not exercised; must not be represented as a live restore drill.
